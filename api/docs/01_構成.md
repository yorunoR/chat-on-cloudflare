# API サーバー構成

`api/` は [Hono](https://hono.dev/) で書かれた Cloudflare Workers アプリケーション。
DB は Cloudflare D1 (SQLite) を使い、[Drizzle ORM](https://orm.drizzle.team/) でアクセスする。
管理画面は [`@sson0-er/drizzle-admin`](https://www.npmjs.com/package/@sson0-er/drizzle-admin) で提供する。

## 技術スタック

| 分類                       | 採用技術                                                      |
| -------------------------- | ------------------------------------------------------------- |
| ランタイム                 | Cloudflare Workers (`wrangler dev` / `wrangler deploy`)       |
| Web フレームワーク         | Hono 4                                                        |
| DB                         | Cloudflare D1 (SQLite)                                        |
| ORM / マイグレーション生成 | Drizzle ORM / drizzle-kit                                     |
| 管理画面                   | @sson0-er/drizzle-admin                                       |
| 運用スクリプト             | Node.js + tsx (`wrangler` の `getPlatformProxy` で D1 に接続) |
| テスト                     | Vitest + @cloudflare/vitest-plugin                            |
| Lint / Format              | Biome                                                         |
| 型チェック                 | TypeScript (`tsc --noEmit`)                                   |
| パッケージマネージャ       | pnpm                                                          |

## リクエストの流れ

```txt
Client
  │
  ▼
Cloudflare Workers (src/index.ts : Hono<AppEnv>)
  │  logger() (全リクエスト)
  ├── ALL  /admin/*         → bodyLimit(1MB) → admin.app (drizzle-admin) → db
  ├── GET  /health          → { "status": "ok" }
  ├── GET  /health/db       → db.run(select 1) → { "status": "ok" }
  ├── POST /api/chat_session → requireUser → zValidator → chat_sessions に insert → 204
  └── GET  /ws/normal_chat/:sessionUid → chat_sessions を uid で検索 (無ければ 404) → WebSocket (runNormalChat で回答をストリーミング)

db (Drizzle) → D1 (binding: DB)
```

### エンドポイント

| パス                              | 説明                                                                                                                                                                        |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /health`                     | プロセスの応答確認。DB には触れずに `{ "status": "ok" }` を返す                                                                                                             |
| `GET /health/db`                  | D1 への疎通確認。`select 1` を実行し `{ "status": "ok" }` を返す                                                                                                            |
| `POST /api/chat_session`          | ChatSession の作成。要認証 (後述)。body は `{ uid, label, initialMessage? }` (JSON)。`uid` はクライアントが採番し、既に使われていれば 409、不正な body は 400、成功時は 204 |
| `GET /ws/normal_chat/:sessionUid` | WebSocket。`chat_sessions.uid` で会話を判別し、存在しなければ upgrade せず 404 を返す。最初に受け取ったテキストメッセージを質問として回答を返す (バイナリは無視)            |
| `/admin/*`                        | 管理画面。Cookie セッションによるログインが必要                                                                                                                             |

### 認証 (API)

`POST /api/chat_session` などユーザーを特定する API には、`requireUser` ミドルウェア (`src/entrypoints/middlewares/require-user.ts`) を付ける。

- `Authorization: Bearer <users.uid>` ヘッダの値で `users` を検索し、見つかれば `c.var.user` に入れる。
- ヘッダが無い・形式が違う・該当ユーザーがいない場合は 401 を返す。
- `GET /ws/normal_chat/:sessionUid` は `requireUser` を通さず、パスの `chat_sessions.uid` で会話を判別する。

`/admin/*` には drizzle-admin がリクエストボディのサイズを制限しないため、前段で `hono/body-limit` により 1MB の上限を設けている。

### ルーティングの構成

- `src/entrypoints/` には外部からの入口となるルート (`routes/`) とミドルウェア (`middlewares/`) を置く。業務処理は `src/apps/` や `src/libs/` に書き、ルートからはそれを呼ぶ。
- 機能・アプリのディレクトリ名 (`routes/<機能>/`, `apps/<アプリ>/`, `scripts/<機能>/`) は URL に合わせて snake_case、ファイル名は kebab-case にする (`prompt_templates.yaml` を除く)。2 つが混ざっているのは意図したもの。
- ルートは機能ごとに `src/entrypoints/routes/<機能>/` に置き、エンドポイント 1 つにつき 1 ファイルの `Hono` インスタンスを作る (例: `health/get-health.ts`, `health/get-health-db.ts`)。
- 機能内のルートは `routes/<機能>/index.ts` で `.route()` をつないでまとめる。
- 機能の接頭辞 (`/health`, `/api/chat_session`, `/ws/normal_chat`) は `src/index.ts` で付ける。
  - REST API は `/api/<機能>`、WebSocket は `/ws/<アプリ>` の下に置く。`/health` と `/admin` は例外として直下に置いている。
- `src/index.ts` ではルートを `.route()` のチェーンでつなぎ、その型を `AppType` として export している。RPC クライアント (`hono/client` の `hc`) が型を拾えるようにするため。新しいルートもこのチェーンに追加する。

### エラー処理・ログ

- `hono/logger` で全リクエストをログに出す。
- `app.onError` で、`HTTPException` はそのレスポンスを返し、それ以外の想定外のエラーは `console.error` に出したうえで `{ "error": "Internal Server Error" }` (500) を返す。エラーの詳細はクライアントに返さない。
- 回答後のログなど、クライアントを待たせる必要のない処理は `runInBackground` (`src/libs/tasks/background-task.ts`) で切り離す。`waitUntil` でランタイムに完了まで待たせ、例外は `console.error` に出す。

### チャットの WebSocket 通信

接続を受けてからの制御は `singleQuestionEvents` (`src/libs/websocket/single-question.ts`) にまとめてあり、ルートは `upgradeWebSocket` にこれを渡して、質問を受けたときの処理 (`runNormalChat` など) だけを指定する。
チャットアプリを追加するときも同じものを使う。

- 1 接続で受け付ける質問は最初の 1 つだけ。2 つ目以降の受信は捨てる。バイナリのメッセージは無視する。
- 回答は `runNormalChat` (`src/apps/normal_chat/normal-chat-controller.ts`) が送り、すべて終わったら `{"done": true}` を送る。接続を閉じるのはクライアントの責務で、`done` を受け取ったら閉じる。
- 質問を受けてから `timeoutSeconds` (`normal_chat` は `normal-chat.ts` の `WS_TIMEOUT_SECONDS` で 300 秒) を過ぎるとサーバーから閉じる (code 1000, reason `timeout`)。想定外のエラーは code 1011 で閉じる。Workers のアダプタは `onOpen` を呼ばないため、接続時ではなく質問の受信時から数える。
- 切断・タイムアウトでは `AbortSignal` で回答の生成を止める。
- upgrade でないリクエストは、DB を引く前に 404 を返す。

## チャットアプリの構成

チャットの処理は `src/apps/<アプリ>/` に置く。`normal_chat` (日常会話) を例に、WebSocket で質問を受けてから回答を返すまでの呼び出しの流れを示す。

```txt
entrypoints/routes/normal_chat/normal-chat.ts   セッションの確認と upgrade
  │
  ▼
libs/websocket/single-question.ts               singleQuestionEvents: 質問の受信・タイムアウト・切断 (AbortSignal)
  │
  ▼
apps/normal_chat/normal-chat-controller.ts      runNormalChat: フローを実行 → 後処理を runInBackground で登録 → done を送信
  │
  ▼
apps/normal_chat/flows/normal-chat-flow.ts      NormalChatFlow: プロンプトテンプレートを取得し、LangGraph のグラフを実行。終了時 (途中終了でも) に質問と回答を chat_messages に保存
  │
  ▼
apps/normal_chat/nodes/normal-node.ts           NormalNode: 会話履歴を取得し、LLM の回答をストリーミングで WebSocket に送る
  │
  ▼
libs/agents/llm-agent.ts                        LLMAgent: システムメッセージ・履歴・入力からチェーン (プロンプト → LLM) を組み立てる
  │
  ▼
libs/external/llm/llm-client.ts                 LLMClient → models/openai-client.ts (OpenAIClient): ChatOpenAI を生成
```

| 層         | 置き場所                        | 役割                                                                                                                                                   |
| ---------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| route      | `entrypoints/routes/<アプリ>/`  | セッションを確認して upgrade する。接続の寿命 (タイムアウト・切断時の abort) は `libs/websocket/single-question.ts` に任せる。チャットの中身は知らない |
| controller | `apps/<アプリ>/*-controller.ts` | アプリの入口。フローを実行し、終わりの合図 (`done`) と後処理を担当する                                                                                 |
| flow       | `apps/<アプリ>/flows/`          | LangGraph でノードの実行順を定義する。使うプロンプトテンプレートの取得と、回答の保存もここで行う                                                       |
| node       | `apps/<アプリ>/nodes/`          | 1 つの処理単位。LLMAgent を使って回答を作り、クライアントへ送る                                                                                        |
| agent      | `libs/agents/`                  | LLM 呼び出しのチェーンを組み立てる (アプリ共通)                                                                                                        |
| client     | `libs/external/llm/`            | LLM プロバイダのクライアント。現在は OpenAI のみ                                                                                                       |

### フローとノードのデータの受け渡し

- LangGraph の State (`history`) には実行したノード名だけを積む。質問 (`prompt`)・回答 (`content`)・最後に回答したエージェント (`lastAgentLabel`) は `FlowData` に持ち、フローが作ってノードに渡したものをノードが書き換える。
- ノードは送信中に例外 (切断・タイムアウト・LLM のエラー) で止まっても、そこまでの回答を `FlowData.content` に移す。フローは `finally` で保存するので、途中までの回答も履歴に残る。
- `ws` に `null` を渡すとクライアントへは送らず、回答だけを返す (テスト・評価・バッチ用)。

### WebSocket で送るメッセージ

`src/libs/websocket/sender.ts` で送る。回答は LLM のチャンクを 3 つずつまとめて送る。

```jsonc
// 回答の途中
{ "message": { "agent": "日常会話担当", "content": "…", "content_key": "message", "stop": null, "cancel": false } }
// 1 つの回答の終わり
{ "message": { "agent": "日常会話担当", "content": "", "content_key": null, "stop": true, "cancel": false } }
// この接続での処理がすべて終わった合図 (クライアントはこれを受けたら閉じる)
{ "done": true }
```

`agent` はプロンプトテンプレートの `label` の値。

## 環境変数・バインディング

型は `src/types.ts` の `Bindings` で定義する。`declare global` で `Cloudflare.Env` を拡張しているため、
`c.env` と `import { env } from "cloudflare:workers"` のどちらでも同じ型が付く。

| 名前                   | 種別              | 説明                                                                                                              |
| ---------------------- | ----------------- | ----------------------------------------------------------------------------------------------------------------- |
| `DB`                   | D1 バインディング | アプリケーション DB                                                                                               |
| `ADMIN_SECRET`         | シークレット      | 管理画面の Cookie 署名鍵。32 文字以上 (`openssl rand -base64 48` などで生成)                                      |
| `SAVE_PROMPT_TEMPLATE` | 環境変数 (任意)   | `true` のとき、使ったプロンプトテンプレートを `prompt_templates` に保存する。ローカル開発用で本番では有効にしない |

- ローカル: `.dev.vars.example` を `.dev.vars` にコピーして値を設定する (`.dev.vars` は git 管理外)
- 本番: `wrangler secret put ADMIN_SECRET` / `wrangler secret put OPENAI_API_KEY` で設定する

### wrangler の環境

`wrangler.jsonc` で D1 データベースを環境ごとに切り替えている。

| 環境       | 選択方法                | D1 データベース名 |
| ---------- | ----------------------- | ----------------- |
| デフォルト | `CLOUDFLARE_ENV` 未設定 | `api_dev`         |
| `ai`       | `CLOUDFLARE_ENV=ai`     | `api_ai`          |

`ai` 環境は AI エージェント用コンテナ (compose の `ai` サービス) からの実行を想定しており、
人間が使う開発用 DB (`api_dev`) と分離するためのもの。どちらも `migrations_dir` は `drizzle`。

## DB 層

### クライアントの生成

`src/db` は Workers と Node.js スクリプトの両方から使えるよう 2 段構成になっている。

- `client.ts` — `createDB(d1)` で Drizzle クライアントを作る。`cloudflare:workers` に依存しないので Node.js スクリプトからも import できる。
- `index.ts` — Workers 用。`cloudflare:workers` の `env.DB` から `db` をモジュールスコープで生成する。生成時点では D1 に問い合わせず、クエリ実行時 (リクエスト処理中) にアクセスする。

Workers 側のコードは `db` を、スクリプト側は `getPlatformProxy()` で得た `env.DB` を `createDB()` に渡して使う。

クエリは、単純なものは呼び出し側 (ルートなど) で `db` に直接書く。複雑なクエリや複数箇所で使うクエリだけ `src/libs/queries/` に置く (repository 層は設けない)。

### スキーマ

- テーブルは `src/db/schema/` に 1 ファイル 1 テーブルで定義し、`schema/index.ts` から export する (drizzle-kit はここを読む)。
- `created_at` / `updated_at` は `columns/timestamps.ts` の `timestamps` をスプレッドして付与する。どちらも unix 秒の integer で、`updated_at` は Drizzle 経由の更新時に自動更新される。

| `user_id`         | integer             | NOT NULL, `users.id` への FK (ON DELETE CASCADE)         |
| `chat_session_id` | integer             | NOT NULL, `chat_sessions.id` への FK (ON DELETE CASCADE) |
| `question`        | text                | NOT NULL                                                 |
| `answer`          | text                | NOT NULL                                                 |
| `created_at`      | integer (timestamp) | デフォルト`unixepoch()`                                  |
| `updated_at`      | integer (timestamp) | デフォルト`unixepoch()`                                  |

#### `prompt_templates`

| カラム       | 型                  | 備考                                                  |
| ------------ | ------------------- | ----------------------------------------------------- |
| `id`         | integer             | PK, AUTOINCREMENT                                     |
| `flow_name`  | text(128)           | NOT NULL                                              |
| `node_name`  | text(128)           | NOT NULL                                              |
| `agent_name` | text(128)           | NULL 可                                               |
| `template`   | text (json)         | NULL 可, テンプレート本体                             |
| `hexdigest`  | text(128)           | NULL 可, `template` のチェックサム (SHA-256 の 16 進) |
| `created_at` | integer (timestamp) | デフォルト`unixepoch()`                               |
| `updated_at` | integer (timestamp) | デフォルト`unixepoch()`                               |

#### リレーション

Drizzle の `relations()` で以下を定義している (リレーショナルクエリ `db.query.*` の `with` で使える)。

- `users` 1 — n `chat_sessions` / `chat_messages`
- `chat_sessions` 1 — n `chat_messages`

ユーザーを削除するとそのセッションとメッセージが、セッションを削除するとそのメッセージが FK の CASCADE で消える。

### マイグレーション

| コマンド                  | 内容                                                                                     |
| ------------------------- | ---------------------------------------------------------------------------------------- |
| `pnpm db:generate`        | スキーマから `drizzle/NNNN_*.sql` を生成 (drizzle-kit)                                   |
| `pnpm db:migrate`         | ローカル D1 に未適用のマイグレーションを適用 (`wrangler d1 migrations apply DB --local`) |
| `pnpm db:status`          | 各マイグレーションの適用状況と down ファイルの有無を表示                                 |
| `pnpm db:rollback [件数]` | 新しい順に指定件数 (省略時 1) を取り消す                                                 |
| `pnpm db:studio`          | Drizzle Studio を起動                                                                    |
| `pnpm db:drop`            | マイグレーションファイルを削除 (drizzle-kit)                                             |
- 適用履歴は wrangler が管理する `d1_migrations` テーブルに記録される。
- ロールバックは独自実装 (`scripts/db/rollback.ts`)。`drizzle/down/<同名>.sql` を実行し、`d1_migrations` の記録を削除する。両者は `db.batch` で 1 トランザクションとして実行される。
- **マイグレーションを追加したら、対応する down ファイルを `drizzle/down/` に手書きで用意する。** 無い場合 `db:rollback` は実行前にエラーで止まり、`db:status` には `MISSING` と表示される。
- スクリプトの接続先はローカル D1 のみ。wrangler の環境は `CLOUDFLARE_ENV` で切り替わる。

## プロンプトテンプレート

各アプリのプロンプトは `src/apps/<アプリ>/prompt_templates.yaml` に `flowName.nodeName.agentName` の 3 階層で書く。

```yaml
normal_chat_flow:
  normal_node:
    normal_agent:
      model_name: gpt-6-luna
      system_message: "ユーザーと楽しくおしゃべりしてください。"
      label: "日常会話担当"
```

`wrangler.jsonc` の `rules` で `*.yaml` を Text モジュールにしているので、YAML は import すると中身の文字列になる (型は `pnpm cf-typegen` が `worker-configuration.d.ts` に生成する)。
各フローのモジュールで import して `setStore()` に渡す。
import のパスはビルド時に解決され、YAML はモジュールとして Worker に同梱される (実行時にファイルは読まない)。パスが間違っていればビルドエラーになる。

```ts
import promptTemplatesYaml from "../prompt_templates.yaml"

setStore(promptTemplatesYaml)
```

`src/libs/prompts/prompt-template-store.ts` で扱う。

- `setStore(yamlText)` — YAML の中身を読み込んでストアに追加する。Workers ではファイルを読めないため、ファイルパスではなく中身を渡す。既に登録済みの `flowName` があるとエラーにする。
- `getTemplate(flowName, nodeName, agentName)` — テンプレートを返す。無ければエラー。
- `getPromptTemplate(flowName, nodeName, agentName)` — `SAVE_PROMPT_TEMPLATE` が `true` なら `getOrCreatePromptTemplate()` で `prompt_templates` に保存したレコードを、そうでなければ保存前の値を返す。

`src/libs/queries/prompt-templates.ts` の `getOrCreatePromptTemplate()` は、キーをソートした JSON (非 ASCII 文字は `\uXXXX` にエスケープ) の SHA-256 を `hexdigest` とし、
同じ `hexdigest` / `flow_name` / `node_name` / `agent_name` のレコードがあればそれを返し、なければ作成する。

## 管理画面

`src/admin/index.ts` で `createAdmin()` を呼び、`basePath: "/admin"` の Hono アプリ (`admin.app`) を作って `src/index.ts` でマウントしている。

### 認証

- ログイン画面の Username にメールアドレスを入力する。
- `verifyCredentials` で `admin_users` を email で検索し、`is_active` かつパスワードが一致すればログイン成功。
- セッション Cookie は `ADMIN_SECRET` で署名される。未設定・32 文字未満の場合はライブラリが起動時にエラーにする。

### 登録モデル

`admin.register(adminUsers, …)` で `admin_users` を管理対象にしている。

- 一覧: `id`, `email`, `isActive`, `createdAt` を表示、`email` で検索可能
- `createdAt` / `updatedAt` は読み取り専用
- `hashedPassword` は password ウィジェット。入力欄は常に空で、変更画面で空のまま保存すると現在の値を維持する
- `validate` で 8 文字未満のパスワードを弾き、`hooks.beforeSave` で平文をハッシュに置き換えてから保存する

ほかに次のテーブルを登録している。いずれも `createdAt` / `updatedAt` は読み取り専用。

| テーブル        | 一覧の表示カラム                            | 検索対象             | 表示名 (`toString`) |
| --------------- | ------------------------------------------- | -------------------- | ------------------- |
| `users`         | `id`, `email`, `uid`, `createdAt`           | `email`              | `email`             |
| `chat_sessions` | `id`, `uid`                                 | `uid`                | `uid`               |
| `chat_messages` | `id`, `chatSessionId`, `question`, `answer` | `question`, `answer` | (既定)              |

新しいテーブルを管理画面に出す場合は、同ファイルで `admin.register()` を追加する。

### パスワードハッシュ (`src/admin/password.ts`)

- Web Crypto の PBKDF2 (SHA-256) を使うため、Workers と Node.js の両方でそのまま動く。
- 反復回数 100,000 回 (Workers の PBKDF2 の上限)、ソルト 16 バイト、鍵長 256 bit。
- 保存形式は `pbkdf2_sha256$<iterations>$<salt hex>$<hash hex>`。
- 検証は定数時間比較で行う。保存値の反復回数が上限を超えるなど不正な形式の場合は `false` を返す。

### 管理者ユーザーの作成

```sh
pnpm admin:create <email>
```

パスワードは実行時に非表示で 2 回入力する (TTY 必須)。同じメールアドレスが既にあればパスワードを更新し、有効化する。

### ChatSession の作成

```sh
pnpm session:create <email> <label> [initialMessage]
```

指定したメールアドレスの `users` に `chat_sessions` を 1 件作る。`uid` にはランダムな UUID を割り当てる。
ユーザーがいなければ作成せず、終了コード 1 で終わる。

## TypeScript 設定

Workers のコードと Node.js スクリプトで型環境が異なるため、tsconfig を分けている。

| ファイル             | 対象                        | 備考                                                                                                    |
| -------------------- | --------------------------- | ------------------------------------------------------------------------------------------------------- |
| `tsconfig.json`      | `src/**`                    | `types: []`。Workers の型は `worker-configuration.d.ts` (`pnpm cf-typegen` で生成、git 管理外) から得る |
| `tsconfig.node.json` | `scripts/**`, `*.config.ts` | `tsconfig.json` を継承し `types: ["node"]` を追加                                                       |
| `test/tsconfig.json` | `test/**`                   | `tsconfig.json` を継承し `types: ["@cloudflare/vitest-plugin/types"]` を追加                            |

`pnpm type` で 3 つともチェックする。Workers 側のコードから Node の API を誤って使わないようにするための分離なので、
Workers と共有するモジュール (`db/client.ts`, `admin/password.ts` など) では `node:*` や `cloudflare:workers` を import しないこと。

import パスには `.js` 拡張子を付ける (tsx で実行するスクリプトと共有するため)。

`package.json` の `imports` で `#*` を `./src/*` に割り当てているので、`src/` 配下のモジュールは
`#db/index.js` のように `src/` を基準にしたパスでも import できる (Node.js の subpath imports)。
階層の深いファイル (`src/entrypoints/routes/...`) から `../../../` のような相対パスを書かずに済ませるため。

`pnpm type` は最初に `pnpm cf-typegen` を実行し、`worker-configuration.d.ts` を作り直してからチェックする。
`wrangler.jsonc` を変えたあとの再生成忘れで、古い型のままチェックされるのを防ぐため。

## 開発

### ローカル起動

リポジトリルートの `compose.yaml` の `api` サービスが `pnpm install && pnpm dev` を実行し、`8787` 番ポートで公開する。

```sh
docker compose up        # または make up
```

コンテナ外で直接動かす場合:

```sh
cd api
cp .dev.vars.example .dev.vars   # ADMIN_SECRET と OPENAI_API_KEY を設定
pnpm install
pnpm db:migrate
pnpm admin:create you@example.com
pnpm dev                          # http://localhost:8787
```

### テスト

```sh
pnpm test         # 1 回実行
pnpm test:watch   # 変更を監視して再実行
```

- `@cloudflare/vitest-plugin` により、テストは Miniflare 上の Workers ランタイムで動く。`src/` のコードを `cloudflare:workers` の `env` を含めてそのまま import できる。
- D1 は `wrangler.jsonc` の `DB` バインディングを使うが、中身はテスト用のメモリ上の DB で、`api_dev` / `api_ai` には触れない。
- マイグレーションは `vitest.config.ts` で `drizzle/` を読み込み、`test/apply-migrations.ts` が各テストファイルの前に適用する。
- `ADMIN_SECRET` は `vitest.config.ts` で固定のテスト用の値を渡しているので、`.dev.vars` が無くても動く。
- テストファイルは `src/` と同じ階層構成で `test/` に置く (例: `src/admin/password.ts` → `test/admin/password.test.ts`)。相対 import には `.js` 拡張子を付ける。
- テストだけで使うバインディングを足したら `test/env.d.ts` に型を追加する。
- 現状テストがあるのは `GET /health/db` と `src/admin/password.ts` だけ。`POST /api/chat_session` やチャット (`/ws/normal_chat`) にはテストがなく、チャットは `pnpm session:normal-chat` による手動確認に頼っている。

### WebSocket の動作確認

```sh
pnpm session:normal-chat <sessionUid> [メッセージ]   # メッセージ省略時は "hello"
```

`/ws/normal_chat/<sessionUid>` に接続してメッセージを 1 回送り、返ってきたメッセージを表示して、`{"done": true}` を受け取ったら切断する。
60 秒以内に `done` が届かない場合、接続エラー時、code 1000 / 1005 以外で閉じられた場合は終了コード 1 で終わる。
`sessionUid` には既存の `chat_sessions.uid` を指定する (`pnpm session:create` で作成できる)。
接続先の基点は環境変数 `WS_URL` で変えられる (既定: `ws://localhost:8787/ws/normal_chat`)。事前に `pnpm dev` でサーバーを起動しておく。

### デプロイ時の注意

- `wrangler.jsonc` の `database_id` は空のため、本番 D1 を作成して ID を設定する必要がある。
- 本番 D1 へのマイグレーション適用は `wrangler d1 migrations apply DB --remote` で行う (`pnpm db:migrate` はローカル専用)。
- `ADMIN_SECRET` と `OPENAI_API_KEY` を `wrangler secret put` で設定しておく。
